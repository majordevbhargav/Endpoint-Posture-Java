# Architecture decision log (proposed)

These are analysis proposals only. No architectural decision has been implemented. Approval is required wherever a public API, deployment topology, security boundary, data retention, or operator workflow changes.

| ID | Related problem | Proposed decision | Rationale | Alternatives | Trade-offs | Affected modules | Dependencies | Reversibility | Approval needed? |
|---|---|---|---|---|---|---|---|---|---|
| D-01 | C-01, R-05 | Define a durable worker operational view with last heartbeat, shard, state, last claim/result, and pending delivery age/count; keep backend service health separate from endpoint worker fleet health. | Existing `/api/v1/system/health` describes the backend and local pool, not endpoint worker delivery. | Extend system health; add an admin worker health endpoint; use external metrics only. | Persisting metrics adds writes/retention; external metrics may not answer per-worker details. | `worker`, `system`, migrations, frontend system/jobs. | Freshness SLO, access policy, cardinality and retention decisions. | Medium; additive schema/API can be rolled back with compatibility plan. | Yes |
| D-02 | C-02, C-08, R-04 | Use server-side paged/filterable job and fleet queries; define stable sort, total/estimated counts, cursor strategy, and bounded export semantics. | Browser-side rows and frequent polling cannot support fleet-scale history. | Keep fixed latest-N lists; use asynchronous report/export job; cursor-only API. | API/schema changes and more query/index work; estimates may replace exact counts. | Job APIs/repositories, endpoint query services, frontend api and tables. | Product filter/sort requirements, Postgres query plans, auth scope. | Medium; additive endpoints are fairly reversible. | Yes |
| D-03 | C-03, C-04 | Treat job/result as a versioned protocol contract shared by backend, worker and scripts; centralize job type capabilities and retain strict execution allowlist. | Prevent drift across independent switch statements and stdout conventions. | Generate DTOs from schema; maintain language-specific DTOs with shared fixtures; keep current mapping plus exhaustive tests. | Protocol governance and compatibility testing; generated code has toolchain cost. | Backend result service/spec factory, worker parser/executor, PowerShell agents. | Ownership of protocol versions and rollout compatibility. | Medium. | Yes |
| D-04 | C-05, R-02 | Document one explicit job state machine and transition owner; preserve attempt fencing, lease expiry and recovery audit as invariants. | State transitions and recovery behavior are spread across services and schedulers. | Keep current decomposition and add state transition docs/metrics only; centralize transition service. | Centralization can create a broad service; minimal change leaves hidden coordination. | Job service/repository, worker service, scheduler, migrations. | Transaction boundaries and concurrency review. | High if first documentation-only, medium for code changes. | Yes for code change |
| D-05 | C-07 | Make authentication/session validity independent from ISE integration readiness; treat ISE as an optional dependency with degraded state. | An ISE failure should not invalidate a valid user session. | Keep current gate but distinguish HTTP 401 from availability errors. | Adds frontend error-state and possibly auth endpoint semantics. | Dashboard layout, API transport/session handling, ISE status context. | Confirm expected login/session behavior. | High. | Yes |
| D-06 | C-06 | Organize frontend API client by domain and remove wrappers only after call-site audit; keep transport/error policy consistent. | Reduce accidental contract mismatch and shallow indirection. | Retain files and document ownership; consolidate into a single large client. | Domain modules add modest structure; single module can become oversized. | Route/type map, current frontend call sites. | High. | No for internal organization; yes if API semantics change |
| D-07 | R-01, R-03, R-06 | Treat Windows worker and Linux backend as separate deployable trust zones with explicit identities, secret lifecycle and verified network paths; choose AWS design before Terraform. | Worker needs Windows, DPAPI and endpoint access; backend needs durable PostgreSQL and API ingress. | Windows EC2 fleet; on-prem workers with AWS backend; hybrid; alternative Windows hosting. | Cost, patching, outbound connectivity, identity, availability differ materially. | Deployment, worker packaging, backend runtime, proxy, AWS. | User/operations/security choice, workload and compliance constraints. | Low after production provisioning. | Yes |
| D-08 | R-02, R-05 | Define 50k endpoint workload and SLOs before selecting shard count, pool sizes, polling, retention and database shape. | Current configurations and seed data do not prove capacity. | Increase resources empirically without targets; introduce queue broker/partitioning now. | Requires load environment and workload model; avoids premature queue infrastructure. | Job scheduling, DB, retention, metrics, infrastructure. | Collection frequency, result size, outage backlog, latency objectives. | Medium. | Yes |
| D-09 | R-03 | Require verified TLS and route/network isolation for production; enable forwarded-header trust only behind the configured proxy. | Current Caddy guidance explicitly conditions proxy trust on firewalling direct app ports. | Terminate TLS in load balancer; service mesh; mutual TLS. | Certificate/rotation operations and deployment coupling. | Spring security/config, Caddy/AWS ingress, worker HTTP client. | Chosen topology and PKI. | Medium. | Yes |
