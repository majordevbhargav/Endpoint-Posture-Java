# Untangle codebase problem inventory

Scope: static analysis of the repository at `8f58b941925dc52687f14af10112a3b896e2b426`. No application tests were run for this analysis. Existing source/tests were inspected only. This follows the Untangle method: identify hidden links, needless links, surplus, special cases, and structural changes that make co-changing pieces explicit. No application code was changed.

## Architecture map and analysis coverage

- **Backend:** Spring Boot application organized by domain packages (endpoint, posture, hardware, diagnostic, indicator, inventory, job, worker, security, ISE, dashboard, system, retention). Controllers define REST contracts; services own orchestration/transactions; repositories use JPA and direct JDBC where needed. `JobWorkerPool`/`JobWorker` execute local jobs in the default profile; worker APIs are a separate authenticated claim/heartbeat/result protocol.
- **Windows worker:** `worker-runtime` is a separate Maven project. `WorkerBootstrap` constructs config, credential store, API client, lifecycle and outbox; `WorkerLifecycle` runs heartbeat/claim/lease renewal/dispatch loops; PowerShell execution is allowlisted and output is parsed into a versioned result; `ResultDispatcher` retries durable SQLite results. `DpapiSecretProtector` uses Windows CurrentUser DPAPI. The analyzed commit contains no worker-specific WinSW service package. Worker service identity, packaging and service-level recovery therefore remain deployment architecture gaps.
- **Data:** PostgreSQL/Flyway migrations V1–V29 define endpoint evidence, current pointers, jobs, inventory, leases, worker identities, recovery events and durable result receipts. SQLite worker schema uses `user_version` migrations, WAL-backed durable pending results, immutable identity/payload triggers and guards against deleting unresolved results. PostgreSQL receipts are transactionally coupled to evidence/job transition and keyed by job/attempt for idempotency.
- **Collection:** PowerShell scripts gather posture, hardware, diagnostic and security-indicator data. Local backend runners and remote worker scripts are distinct execution paths; they share domain ingest models but not one process boundary. Worker output is captured with limits, process timeout/tree termination, and explicit `RESULT_JSON:` schema validation.
- **Frontend:** Next.js 16 App Router with typed fetch clients; route-to-controller mapping is covered in `docs/frontend/frontend-audit.md` and `page-and-component-plan.md`. API origin is proxied through build-time Next rewrite configuration.
- **Deployment:** `docker-compose.yml` is a development composition: PostgreSQL/Adminer plus optional frontend; backend runs on the host. Caddy reverse-proxy guidance exists. Repository search found no Terraform (`*.tf`) or CI workflow definitions; the AWS guide is documentation, not executable infrastructure. No deployment behavior was changed.
- **Tests:** backend/worker/frontend test source was inventoried but not executed as part of this static architecture analysis.

## Confirmed positive design evidence

- Worker enrollment tokens are random, stored as SHA-256 hashes, single-use/expiring by atomic update; worker API keys are also hashed; authenticated workers can be revoked, and heartbeat freshness is derived using configured stale thresholds (`WorkerRegistryService`). Admin worker list exposes `lastSeenAt` and ACTIVE/STALE/REVOKED state. This is real API functionality but the frontend has no worker registry page.
- Worker job renew/complete/fail operations are fenced by worker claim identity and attempt; result submission checks ownership and type, locks the lifecycle row, validates envelope, hashes canonical request and atomically stores evidence, lifecycle transition and durable receipt (`WorkerJobService`, `WorkerResultService`, migrations V25/V29).
- Worker SQLite stores immutable payload and SHA-256, bounds delivery retries/lease extensions, and prevents deleting unresolved results (`SqliteJobResultHandoff`). These are implementation properties, not proof of actual Windows service restart recovery.
- PowerShell script names are allowlisted and resolved under the configured script directory; output streams are bounded and process trees are terminated on timeout/interruption (`PowerShellExecutor`).
- Auth separates human JWT, worker key, agent API key and ISE Basic-auth paths; controllers apply role restrictions and Actuator Prometheus requires ADMIN in Spring Security. Production network-level exposure remains environment dependent.

Severity: Critical blocks safe production operation; High materially blocks readiness or scale; Medium adds a maintainability or operational risk; Low is a localized quality opportunity. Confidence expresses evidence confidence, not severity.

## Special cases recorded

- `application-linux.yml` disables the local worker pool and uses `REMOTE_PENDING` while remote workers are handled through a separate protocol.
- Worker lease durations and maximum extensions are clamped/configured; renewals are attempt and ownership fenced.
- A successful API acknowledgement is replayed only for the same worker, attempt and canonical result hash; historical receipts intentionally outlive job lifecycle rows.
- PowerShell output accepts the last `RESULT_JSON:` line, while script paths are restricted by an explicit allowlist and canonical path check.
- Worker result `FAILED` accepts a null report payload, but success/partial paths require typed payloads and matching process outcome metadata.
- DPAPI uses CurrentUser scope, so enrollment and service execution must use the same Windows identity/profile; this source-level invariant does not itself prove restart recovery.
- Frontend dashboard bootstrap uses ISE status as its readiness gate.
- UI polling intervals differ by page (jobs 4s, other health views 10–20s); this may be intentional but is not yet driven by a stated freshness SLO.
- In-process table pagination/export is mixed with server-paged endpoints.

These are either deliberate safety rules or special-case behavior to verify; the inventory does not recommend removing a security fence merely to reduce branching.
